The defects

1. Missing-stop openPositionRisk booked the full notional P0

lossAccounting.tsTradingBudgetReader.ts openPositionRisk used stopPrice ?? 0, so a long with no stop computed entry − 0 = entry and booked entry × size as risk — exhausting the budget instantly. stopPrice is genuinely optional on the contract; every record written before migration 040 has stop_price IS NULL, so this was live-reachable.

Fix: when either price is undefined, the stop-distance term contributes 0 (unknown loss, not zero-priced). Fee and slippage terms always count. Three artefacts that pinned the wrong behavior as "BY DESIGN" were deleted/inverted; the budget-reader test now feeds the output through evaluateLossBudget and asserts the budget is not exhausted. The reader's stop-fetching subquery was also hardened from mission-wide-latest to a market-correlated, status-filtered scalar subquery.

Probe: openPositionRisk({direction:"long", size:1, weightedEntryPrice:3000, stopPrice:undefined}) → was 3000, now the fee terms only.

2. tools.test.ts red gate gate

tools.test.ts The sorted tool-name gate was never updated when trading_request_entry landed, leaving pnpm test red on main. Added TRADING_REQUEST_ENTRY_TOOL (the exported constant, per file convention) in sorted position. Predated the Phase-4 close-out; not a regression from it.

3. buildCancelByCloidAction missing type + wrong key P0

OrderMapper.ts Returned { cancels: [{ coin, cloid }] } — no type, and the leg used coin (symbol) instead of asset (numeric index). Verified against the Hyperliquid exchange-endpoint docs and hyperliquid-python-sdk: the canonical shape is { type: "cancelByCloid", cancels: [{ asset, cloid }] }. Same class of defect as the order-path type:"order" fix. This action is live-reachable via blockForExhaustion and had never been sent live.

Fix: signature now (assetIndex, cloid); the caller resolves the index via gateway.resolveMarket (same as the order path). The guard's silent Effect.catch(() => Effect.void) swallow was replaced with catchTag + warn-level logging (cloid + exchange reason) so a failed cancel is visible, not silent.

4. Cloid bare-hex form was silently dropped by the exchange P0

Cloid.ts deriveCloid returned a bare 32-char hex string. Reading the live Gate E entry (oid 57307761690) back via the Info API showed the exchange stored "cloid": null — the bare form was dropped, so retry-dedup rested entirely on local idempotency-key convergence. Verified against the SDK's Cloid.to_raw(): the wire shape is 0x-prefixed 34 chars (16 bytes). Our bytes were correct; only the prefix was missing.

Fix: deriveCloid returns 0x${hex}. Applied at the single boundary so one representation flows everywhere (DB column, reconciler join, UI slice). After the fix, the live retry produced no second order — exchange-side dedup is now effective.

5. Order wire used cloid where the canonical form is c P0 root cause of the live failure

OrderMapper.ts This was the root cause of the live Gate E failure and the original "sell-action signature recovers to a wrong address" symptom from commit 5dfb4bc14. buildOrderAction emitted the client order id under key cloid inside the order leg; the canonical Hyperliquid wire format uses key c (verified byte-for-byte against hyperliquid-python-sdk's order_request_to_order_wire; the cancel-by-cloid top-level leg genuinely uses cloid).

The wrong key changed the msgpacked action bytes → the action hash → the EIP-712 digest → the signature. The signature was self-consistent with the malformed action (offline EIP-712 recovery matched), but the exchange hashes the canonical c shape, so it recovered a different address and rejected with "User or API Wallet <wrong addr> does not exist."

Reference-vector comparison (hardhat test key, hyperliquid-python-sdk 0.24.0): the EIP-712 domain (chainId=1337), action-hash construction, agent struct hash, and signature shape all match the SDK byte-for-byte. Signing.ts was exonerated and not edited. The one-line fix (cloid → c) made our action hash match the SDK's exactly.

Added 4 cases on the real guard + real execution service + recording fakes: cancel-only-increasing, swallow-and-log-on-failure, reduce-only-submit-shape, close_did_not_flatten escalation.

Task 7 The §16.4 blocked-mission control matrix (revoke/pause permitted, resume rejected, reconcile-before-resume) was missing — the exact bug B4 fixed. Added 4 cases on the existing TestLayer.

Task 8 The end-to-end reachability chain (trading_request_entry → command → decider → event → reactor → exchange → reconcile → projection) had no test. Added TradingExecutionReachability.integration.test.ts, solving the genuine TradingLayerLive overlay blocker by rebuilding the trading layer with fakes at the foundation.

What was not the problem

Signing.ts is correct. The prompt froze it on suspicion, and the reference-vector comparison exonerated it: the EIP-712 phantom-agent domain (chainId=1337), the action-hash construction, the agent struct hash, and the signature shape all match hyperliquid-python-sdk byte-for-byte. The "wrong address" symptom was a wire field-name bug in buildOrderAction (action-construction territory, not the frozen hashing/EIP-712 code). Signing.ts and Msgpack.ts were not edited.
