The WebSocket connection logic of T3 Code

One socket. One JSON-RPC surface. A supervisor-driven state machine on the client, a scope-bound event-sourced core on the server, and three transport modes that all converge on the same handshake. This report is a forensic walkthrough of how a T3 Code client stays connected to a T3 Code environment — and what happens when it doesn’t.

The one-sentence model

The browser never calls new WebSocket directly. A supervisor in packages/client-runtime owns the socket, authenticates each upgrade with a 5-minute HMAC wsTicket, and feeds a single JSON-RPC group (WsRpcGroup) whose streaming methods are the entire push channel. Big read-model snapshots go over gzip-compressed HTTP; the socket carries only small live deltas.

01 Architecture map

Six layers, top to bottom. The thin client surface injects capabilities; the shared runtime owns the socket; the contract defines every message; the server authenticates, dispatches, and streams; providers run as subprocesses; git refs persist checkpoints at end-of-turn.

Why this shape

Complexity lives at the adapter boundary (provider stdio ↔ runtime events). Orchestration stays pure (decider + projector), the wire stays dumb (schema-defined RPC), and the client never trusts the socket (supervisor probes + sequence-resume).

03 Server lifecycle

A single Effect HttpServer hosts one ws WebSocketServer (noServer: true, Effect.cached). Per-connection state is a refcounted session map, not a set of sockets. T3 deliberately disables Effect’s 20-second HTTP drain so WS finalizers run immediately on shutdown.

return yield* Effect.acquireUseRelease(
  sessions.markConnected(session.sessionId),
  () => rpcWebSocketHttpEffect,
  () => sessions.markDisconnected(session.sessionId),
);
Connection tracking
Ref.make(Map<SessionId, count>) — refcounted.
Multiple tabs = multiple sockets, one session. The "connected" flag only flips at zero.
Graceful shutdown
HTTP_PREEMPTIVE_SHUTDOWN_GRACE_MS = 0
Per-WS acquireRelease closes sockets; no artificial drain.
Footgun — refcount composite isn't atomic

markConnected does atomic Ref.modify for the count, but the surrounding “load session + emit upsert” is eventually-consistent. Two concurrent connects for one session can each publish; a failed emit is swallowed (Effect.catchCause logs only) and desyncs the UI’s session list without breaking the socket.

How a malformed message is handled

Effect’s RPC loop (RpcServer.js:440-515) is the only validation surface. Every bad input becomes a typed defect on the matching requestId — nothing kills the socket or the process.

Failure Response Outcome
Unknown method tag sendRequestDefect("Unknown request tag: …") typed Exit.Failure
Payload schema fail sendRequestDefect(issue.toString()) typed Exit.Failure
Bad request id sendDefect("Invalid request id") connection survives
Unknown envelope _tag sendDefect("Unknown request tag") connection survives

04 Pairing & authentication

The WS upgrade authenticates via a short-lived HMAC wsTicket query parameter (5-minute TTL, session-bound, revocation-checked). That ticket is minted from a session that began life as a pairing code — a 12-character string over an ambiguous-char-free alphabet.

Acknowledged trade-off

The wsTicket rides in a query parameter. Query strings are commonly logged by proxies/CDNs. The 5-minute TTL and single-purpose scope mitigate but do not eliminate log-leak risk — which is exactly why tickets exist instead of putting a long-lived bearer in the URL.

Signing key rotation

server-signing-key is a random 32-byte value persisted via ServerSecretStore.getOrCreateRandom. It is not rotated automatically; rotating it invalidates every outstanding session and WS ticket. The cloud-mint keypair (for T3 Connect) is provisioned once via Alchemy and supports multi-key verification for rotation (EnvironmentConnector.ts:203-224 tries all stored public keys).

05 Connection state machine

A single supervisor fiber per environment owns the socket. It is driven by a typed signal queue and exposes two status layers: an inner phase (SupervisorConnectionPhase) and a UI projection (EnvironmentConnectionPhase) that distinguishes “connecting” from “reconnecting”.

available connecting reconnecting backoff connected offline blocked (error)
available
No active connection, no attempt in flight. Entry state and post-disconnect resting state. Trigger: ConnectRequested signal → connecting.
connecting
Preparing → opening → synchronizing (driver staging). Raced against a 15s establishment timeout and any interrupt signal. On success: → connected. On transient failure: → backoff.
backoff
Sleeping before next attempt. Delay = retryDelayMs(failureCount). Interruptible: a manual retry, network change, or wakeup signal breaks the sleep immediately. UI projects this as reconnecting.
connected
Socket open, initial serverGetConfig succeeded, probe registered. The run loop races session.closed against the active-lease monitor. Reset window: held ≥30s → failureCount = 0.
offline
navigator.onLine === false (or RN equivalent). Supervisor parks here, aborts in-flight establishment, and waits for the network to return. Not a retry-eligible state.
blocked
ConnectionBlockedError — auth/permission/config/unsupported. Does not retry; waits for a signal (credential refresh, user action). UI projects this as error.
Why "reconnecting" is a distinct UI phase

connecting projects to "connecting" only when attempt ≤ 1 && lastFailure === null; otherwise to "reconnecting". A user seeing “Connecting…” on a 6th retry would be lied to. The failure reason is appended: “Failed to connect. Reconnecting… Reason: <error>”.

The signal queue (5 signal types)
Signal Source Effect
ConnectRequested registry acquire, manual connect start an attempt
DisconnectRequested user/env removal tear down, go available
RetryRequested manual retry button interrupt backoff sleep / probe
NetworkChanged online/offline events park offline, or resume
Wakeup tab visible · credentials-changed probe liveness or force reconnect

06 Backoff & liveness

Pure exponential, no jitter, no cap on attempts. Three independent 15-second timeouts guard three different layers. There is no continuous keepalive; the socket is probed on demand when the app reactivates.

Pinned at 16s after the 5th failure. Resets to 0 only after a connection held ≥30s (BACKOFF_RESET_AFTER_MS). No jitter means simultaneous clients can thunder-herd on a server restart.

Gap — no continuous liveness bound

A foregrounded tab with pings flowing but a silently-stalled reactor will show "live" indefinitely. The 5s ping only proves transport liveness, not event-stream liveness. Detection requires a user action (visibility change → probe) or a transport failure.

What the 5-second ping actually does

Effect’s RPC client (RpcClient.js:718-738) runs a pinger:

  1. Every 5s, if the previous pong arrived, send Ping.
  2. If no pong arrived, open a latch — pinger.timeout resolves.
  3. makeProtocolSocket races the read loop against pinger.timeout.
  4. Timeout → SocketOpenError({kind:"Timeout", cause:"ping timeout"}).
  5. T3’s Effect patch adds an onPingTimeout hook that fires before the failure.

The server only ever responds to pings (RpcServer.js:487-490); it never initiates. A half-open server-to-client direction is invisible until the client’s own ping fails.

Coalescing protects the shell stream

Stream.groupedWithin(512, 50ms) + per-aggregate dedup means a burst of 50 token deltas for one thread collapses into a single shell refetch (SHELL_COALESCE_WINDOW = 50ms, SHELL_COALESCE_MAX_CHUNK = 512). The live buffer is attached before the snapshot read so events in flight aren’t lost.

All queues are unbounded

Every queue and PubSub in this chain is unbounded. A slow WS client or stalled reactor accumulates memory. The design assumes consumers keep up; the only safety net is scope-based cleanup on disconnect. The 5s ping timeout bounds it in practice.

Checkpointing & receipts

At turn completion, CheckpointReactor captures a hidden git ref: 

# refs/t3/checkpoints/<base64url(threadId)>/turn/<turnCount>
git read-tree HEAD   # into a temp GIT_INDEX_FILE
git add -A -- .
git write-tree
git commit-tree <tree> -m "t3 checkpoint ref=…"
git update-ref <checkpointRef> <commitOid>

The finalized turn diff flows to clients via a thread.turn.diff.complete domain event (in the isThreadDetailEvent set). RuntimeReceiptBus publishes typed receipts — but the production layer is a no-op; receipts exist purely for test determinism. End-of-turn completion is signaled to clients by the domain event, not a receipt.

10 Subscriptions & resume

There is no global broadcast primitive. Every server→client push is the success schema of a streaming RPC the client explicitly subscribed to. The strongest part of the design is how these subscriptions survive reconnects: subscribeDynamic re-binds to whichever session the supervisor currently holds, and resumes by sequence.

Re-subscribe on session change
SubscriptionRef.changes(supervisor.session) → Stream.switchMap. A new connection automatically re-issues every active subscription with a freshly-computed input.
Resume by sequence, not replay
Client loads HTTP snapshot, passes afterSequence. Server replays only the gap; falls back to a fresh snapshot if gap > 1000.
Transport-failure resilience
A stream that fails with only RpcClientError reasons logs a warning and drains — it waits silently for the next session rather than failing the subscription. UI atoms are oblivious.
No outbound queue
A dispatchCommand while offline fails fast with EnvironmentRpcUnavailableError. Nothing is buffered. The composer surfaces this as a send failure — not a silent outbox.

11 Web · Desktop · Mobile

There is no surface-specific WebSocket code. All three share one connection stack in packages/client-runtime. Each surface differs only in (a) which WebSocket constructor it provides, (b) which platform capabilities it injects, and (c) how it bootstraps the list of environments.

Web (browser)
Browser’s native WebSocket.

Has a primary? Only if window.desktopBridge is present (desktop renderer). Hosted app.t3.codes has none — every environment is user-added remote.

Poll: 3s PLATFORM_POLL_INTERVAL for desktop bootstraps (no change event).

Connectivity: navigator.onLine + window events.
Desktop (Electron)
Same renderer as web. Hosts the server as an ELECTRON_RUN_AS_NODE=1 child via fd3 bootstrap.

WS server is the bundled apps/server — Electron main never creates one. The renderer connects to its own server the same way it connects to any remote.

Exposure: LAN (0.0.0.0) · Tailscale Serve · T3 Connect relay. Mode changes require relaunch (bind host fixed at spawn).
Mobile (React Native)
RN’s built-in global WebSocket via Socket.layerWebSocketConstructorGlobal. No native WS module, no fallback.

Never hosts. No primary. SSH hard-blocked. All connections are bearer or DPoP-relay.

Background: OS kills the socket. Recovery is the foreground probe. A 25s activity report + 45s server lease keeps server-side awareness.
