What is genuinely done and proven: the byte-critical foundation — execution contracts, nonce lane, deterministic cloid, msgpack + EIP-712 signing, exchange client, order mapper, the six loss-budget equations, the 17-item preview checklist, and the six §18 tables. The signing path is live-accepted by the Hyperliquid testnet (a signed noop returned {"status":"ok"}). Risk is reserved before signing; retries reuse a deterministic cloid + idempotency key.

What is NOT done — and is load-bearing for the phase's stated purpose:

  • No end-to-end flow. The decider emits only 4 trading commands (mission lifecycle). There is no trading_place_order / trading.execution.requested command or event, and the reactor never calls submitOrder. A harness entry request cannot reach the exchange through T3 orchestration today.
  • Reconciliation is dead code. HyperliquidReconciler reads canonical fills/position/orders correctly, but none of its 8 §18.2 triggers is ever fired. submitOrder does not reconcile after submission; reduceOnlyClose stubs it with void reconciler;
  • UI cards render nothing. The three cards exist and are correctly wired to the projection, but the projection hard-codes them to null/[]. No join reads the migration-037 tables.
  • Exhaustion enforcement is unwired at runtime. The policy is correct and enforced at preview, but the guard service (guardResume, blockForExhaustion) has zero live callers — a blocked mission can be resumed without revalidation.

Net: PROMPT-04 delivers a correct, tested, live-proven execution library, but not yet an execution feature. The wiring that turns the library into the phase's promised behavior is the remaining work.

The missing end-to-end flow (the decisive gap)

This is the single most important finding. PROMPT-04's purpose is to "turn the resumed harness's typed entry requests into validated, signed, idempotent orders." That sentence describes a flow from the harness to the exchange. The flow does not exist yet.

What the spec promises

harness entry request
  → decider: trading.execution.requested event
  → reactor: TradingExecutionGuard.guardAction
  → HyperliquidExecutionService.submitOrder  (preview → map → persist → sign → POST → inspect)
  → HyperliquidReconciler.reconcile          (canonical fills/position/orders → DB)
  → projection refresh                       (→ UI cards render real data)

What actually exists

harness entry request
  → ✗ no decider command/event for execution
  → reactor handles ONLY mission create/pause/resume/revoke/status/strategy
  → HyperliquidExecutionService.submitOrder is callable only by a direct Effect call
  → the sole in-repo caller is TradingExecutionGuard.reduceOnlyClose
  → reduceOnlyClose has NO caller, and stubs the reconcile step
  → projection hard-codes execution surfaces to null/[]  → UI cards never render

The decider is the seam. apps/server/src/orchestration/decider.ts:1266 ends with default: command satisfies never — adding execution commands is a compile error until the decider is extended. This is an intentional, type-safe boundary. The prior report explicitly defers trading_place_order / trading_resume_mission to PROMPT-05, but that deferral is not visible in the prompt text itself — it is a scoping decision made during the session.

Inert components — built, layered, never called

Three services are correctly constructed and composed into TradingLayerLive (runtimeLayer.ts:87-92), so they are instantiated at runtime — but no live code path invokes them. They are the difference between "the library works" and "the feature works."

Note: the live-gated signing path (executionSmoke.test.ts) does exercise signL1ActionForWire + exchange.submit directly — that is the live-accepted proof. The inertness is about the orchestration path, not the crypto.

What remains (prioritized)

  1. Wire the execution command/event into the decider (the compile-enforced never seam). Add trading.execution.requested (or trading_place_order) and a reactor handler that calls guardAction → submitOrder. This unblocks the end-to-end flow and acceptance criterion #2.
  2. Fire the reconciler from submitOrder on the after_submission trigger, and add the after_fill / websocket_reconnect / periodic_while_position_open hooks. Persist fills + open orders, not just the position snapshot. Add the missing unit tests.
  3. Extend the projection (TradingMissionProjection.refresh + a 036 column extension or a join to the 037 tables) so the three UI cards render real data. Add liquidationPrice to the position contract/table/card.
  4. Wire runtime exhaustion enforcement: call blockForExhaustion when the budget hits zero, and gate mission resume through guardResume in the reactor.
  5. Finish reduceOnlyClose — replace void reconciler; with a real reconcile-to-flat, and give it a caller.
  6. Fill the two preview no-ops (items 4 & 8) or explicitly document why they are enforced elsewhere (and remove them from the checklist if so).
  7. Minor hardening: assert status==="ok" in the smoke test; test the no-double-count invariant for paidFeesUsd; add a positive min-notional boundary test; add a dedicated file-fallback test for InterimSignerConfig.

Recommendations

  • Scope honesty. The prior report's "done" framing for Steps 7, 9, 10, 11 overstates reality: components exist but are not wired. Treat the decider/reactor integration as part of PROMPT-04, not a deferred PROMPT-05 concern, unless the owner explicitly confirms the deferral — the prompt text does not contain it.
  • The signing path is the real milestone. The live-accepted noop is a genuine, hard-won result (the two bug fixes — uint256 domain separator and {r,s,v} wire form — are correct and implicitly pinned by the recovery-based test). This is the riskiest part of the phase and it is sound.
  • Reconciler is the next highest-risk item. "Local state must never outrank the exchange" is a core invariant; today local state is the only state, because reconciliation never runs. Wire it before any live order beyond the smoke probe.
  • Do not run a real order through the current path until reconcile-after-submission is wired — the position/fill cards will lie to the UI, and a retry-after-disconnect has no convergence guarantee.
