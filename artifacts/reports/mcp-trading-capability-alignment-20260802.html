Is MCP the right choice for trading?

One question, framed against T3 Code itself: how capabilities reach the agent.

Assessment
Architecturally aligned by precedent—not transport-identical. Keep trading on MCP.

The transports are mechanically different, but the difference is justified. Providers supply their own integral coding tools; T3 normalizes their events and routes responses. Upstream T3 Code’s closest first-party precedent for an auxiliary, provider-neutral capability is its optional preview MCP toolkit. Applying that precedent to T3-owned trading is a repository-grounded inference, not a claim that every T3-owned extension must universally use MCP.

How T3 Code exposes coding capabilities

Short statement

Upstream T3 Code uses MCP for no integral coding capability. File edits, patch application, and shell commands come from the selected provider’s native tool surface. T3’s adapter translates provider-native lifecycle and approval messages into canonical events, and the provider service routes the user’s decision back to the owning provider adapter. Upstream’s first-party MCP use is the optional, auxiliary preview browser toolkit.

Why CanonicalRequestType is not a capability API providerRuntime.ts:135–146, 421–433

The schema names normalized categories for provider-originated interactive requests—command execution, file read/change, patch, and command approvals. Those values populate request.opened and request.resolved payloads. They describe and route an interaction after a provider has exposed a tool; they do not register a new tool with an agent.

Together, the evidence shows coexistence rather than coding actions traversing MCP.

How T3 Trade exposes trading capabilities

Short statement

T3 Trade defines all 14 inspected agent-facing trading operations as one MCP toolkit. Its handler layer implements that toolkit, and McpHttpServer registers it beside the existing preview toolkit on the same first-party /mcp transport. Within the inspected agent-facing surface, no second trading capability transport is defined.

The first-party MCP session is injected across provider adapters Codex · Claude · Cursor · Grok · OpenCode

The adapters conditionally inject the same t3-code MCP endpoint into Codex, Claude, Cursor, Grok, and OpenCode sessions. That concrete cross-provider wiring is why the existing MCP boundary is a suitable delivery mechanism for a T3-owned toolkit.

Same transport? No. Same architecture? Yes.

Mechanically different

Coding is provider-native

Codex, Claude, and other providers already own the coding tool surface. T3 adapts their native requests into a common runtime model.

Architecturally aligned

Trading is a T3 extension

Trading is owned by T3 Trade and must reach whichever provider is active. Preview supplies the closest existing first-party precedent, and the adapters already inject that MCP endpoint across providers.

The relevant T3 Code comparison is ownership, not “every world-changing action uses one transport.” Provider-owned integral coding tools stay native. For trading, reusing the cross-provider MCP wiring and preview precedent is the smallest consistent extension. Moving trading into CanonicalRequestType would confuse normalization of provider-originated interactive requests with tool registration, and would require inventing provider-specific trading integrations without a coding-side precedent.

Answer: MCP is the right choice. This is not transport parity with coding; it is a justified, repository-consistent use of the closest T3 Code precedent. No trading transport rewrite is indicated. The useful follow-up is to make the boundary explicit in documentation and keep it covered by focused registration/contract tests.

Prompt to proceed

If follow-up work is desired, this keeps it at the capability-delivery boundary established by the evidence: 

Proceed without rewriting the trading capability transport. Keep all 14 trading capabilities on T3 Trade’s first-party MCP toolkit, registered beside preview on the existing /mcp boundary.

Make only boundary-clarifying changes:
1. Add a short architecture note explaining that provider-owned coding tools remain native and are normalized through ProviderRuntime/ProviderAdapter, while trading follows the closest T3-owned precedent: the optional preview toolkit on the cross-provider first-party MCP boundary.
2. Add or tighten focused tests that assert the trading toolkit’s 14 tool names and its registration beside preview on the MCP server.
3. State explicitly that CanonicalRequestType is for normalizing and routing provider-originated interactive requests, not for registering trading capabilities.

Do not add trading request types to CanonicalRequestType, build provider-specific trading adapters, or move trading off MCP. Stay strictly on how capabilities reach the agent; do not analyze security, signing, budgets, or the execution loop.

Scope and exclusions

  • In scope: provider-native tools, canonical event/request normalization, provider response routing, MCP toolkit registration, and the preview precedent.
  • Explicitly out of scope: security, signing, capital controls, budgets, and execution-loop design.
  • Evidence boundary: conclusions are limited to the inspected provider contracts/adapters and the server’s preview/trading MCP toolkits. No claim is made about whether an individual trading operation is otherwise well designed.
