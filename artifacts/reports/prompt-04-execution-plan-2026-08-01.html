Execution plan · PROMPT-04 · finish the wiring

Turn the proven signing library into the live execution feature

This plan covers only what remains. The byte-critical foundation is built and the signing path is live-accepted by the Hyperliquid testnet. What's missing is the wiring that turns that library into the phase's promised behavior: a harness entry request must flow through the decider, get signed, reach the exchange, and return reconciled fills/positions to the UI. The order below is a dependency chain — each milestone unblocks the next. Do not reorder.

Milestones

Five slices, each independently reviewable. M1 is the keystone — it creates the seam the rest plugs into. M2 makes state converge. M3 surfaces it. M4–M5 harden the risk envelope. M6 is the single live proof that unlocks the phase.

M1 · first

Execution command & event in the decider

Add trading.execution.requested (command) and a matching event to the decider. The decider is exhaustive over 4 trading commands today — its default: command satisfies never makes this a compile-enforced seam. Wire a reactor handler that calls TradingExecutionGuard.guardAction → HyperliquidExecutionService.submitOrder. This is the one change that creates an end-to-end path from harness request to signed order.

Open questions

Is the execution command part of PROMPT-04 or deferred to PROMPT-05?
The repo's prior report defers trading_place_order to PROMPT-05, but the spec's step map and exit-evidence ("local position converges to canonical exchange state") place reconciled execution squarely in PROMPT-04. The design note (trading-execution.md) lists Steps 6–10 as PROMPT-04 outputs. Resolve with the owner before starting M1 — it determines whether this plan is "finish the phase" or "start the next."
Decide with · owner, before M1
What emits the after_fill trigger?
Fills arrive via WebSocket user-channel subscription or polling. The repo has a WebSocket client but no per-user fill subscription wired to the trading layer. Decide: subscribe on mission-enter, poll on a timer, or both. This affects M2's fill-handler design.
Decide with · implementer, during M2
Preview items 4 & 8 — enforce here or document the deferral?
authority_version_current and execution_wallet_approved are pass-through no-ops today. If enforcement lives elsewhere (e.g. authority is checked at mission resume), cite where and drop them from the 17-item list. Otherwise implement them. A checklist item that always passes is a latent bug.
