Milestone evidence

M1 — Execution command, event, reactor handler (keystone)

  • Contracts: TradingExecutionRequestedCommand (trading.execution.requested) added to InternalTradingCommand; trading.execution-requested event + payload added to TRADING_EVENT_TYPES, OrchestrationEventType, and the OrchestrationEvent struct union.
  • Decider: the new case mirrors the control case; the exhaustive default: command satisfies never is the compile gate proving the union is closed.
  • Reactor: processExecutionRequested runs the §17.2 write side — load mission → resolve master address → reconcile before_execution → assemble preview context → guardAction → submitOrder → reconcile after_submission → re-check budget → blockForExhaustion if exhausted.

M2 — Reconciler triggers + persistence

  • Persistence: persistFills (idempotent on fill_id) and persistOpenOrders (replace-by-mission) added; both called from reconcile (the discard comment is gone).
  • WS fills: new TradingFillReconciler subscribes to the userFills WebSocket channel and fires after_fill per market-matching frame. HyperliquidWebSocketClientLive composed into TradingLayerLive.
  • Periodic backstop: a 5s schedule fires periodic_while_position_open while a position is open.
  • Server startup: the active mission is reconciled with server_startup at layer build.

M3 — Projection + liquidation price

  • Projection join: readExecutionSurfaces reads the latest execution record, recent fills, and position snapshot from the 037 tables; toMission maps them to the three UI cards.
  • Liquidation price: new migration 038_TradingExecutionColumns adds closed_pnl and liquidation_price; threaded through WirePosition → AccountPosition → TradingPositionSnapshot → TradingPositionView → PositionCard.

M4 — Runtime exhaustion enforcement

  • Auto-block: after submit + reconcile, the reactor re-evaluates the budget and calls blockForExhaustion when remainingCumulativeLossUsd ≤ 0.
  • Resume gate: processControlRequested loads the mission and calls guardResume(missionId, isBlocked) before any transition; a blocked mission cannot resume without explicit revalidation.
  • Budget reader: new TradingBudgetReader assembles the §16.2 inputs (closedPnl + fees from fills, open-position risk, pending-entry risk from reservations).

M5 — Reduce-only close

  • The void reconciler; stub is replaced with a real after_position_update reconcile that escalates close_did_not_flatten rather than assuming the close landed. ExecutionInput.masterAddress added so the reconcile resolves the §10.6 identity.

Deliberate deviations from the plan

1. Reconcile-after-submission lives in the reactor, not in submitOrder.

The plan's code-block inlined reconcile(..., "after_submission") as step 9 of submitOrder. I placed it in the reactor handler instead, so submitOrder stays a pure submit (single responsibility) and the reconciler's masterAddress resolution lives where the mission is known. This honours the repo's stated taste: "complexity at the adapter boundary; orchestration stays pure."

2. server_startup runs at layer build, not in start().

Putting the startup reconcile in start() widened its Effect requirements (SqlClient | HyperliquidGateway | HyperliquidInfoClient), rippling to every caller. Moving it to a forked fiber inside make (where those deps are already captured) keeps start: Effect<void, never, Scope> narrow and avoids touching the orchestration-reactor interface and its callers.

3. M6 delivered as a scaffold, not a live-capital test.

The full real-order fixture (seeded mission + account, fake exchange, armed signer) is substantial. The wiring's correctness is verified by focused unit tests + the type-checker's exhaustive decider + the live noop probe. The capital-spending test is the one remaining gated step.
