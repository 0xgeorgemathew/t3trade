1 · The big picture

Upstream T3 Code is an open-source GUI that supervises coding agents (Codex, Claude, Cursor, Grok, OpenCode) against a git workspace, with desktop/web/mobile clients. This fork — T3 Trades — keeps every bit of that and adds a Hyperliquid trading overlay on top. The clever move: it does not build a second server. It reuses the existing event-sourced orchestration engine, so a trading mission is just a new aggregate type flowing through the same decider → projector → reactor pipeline that already handles chat threads.

The headline architectural idea, and the thing that makes the whole system coherent:

The wake loop is the product. When a market watch fires, the server resumes the same provider session (e.g. the same Claude conversation) and hands it a fresh, bounded market snapshot. The coding agent wakes up, reads the situation, decides, and calls a trading tool — which flows back through the event engine, signs server-side, and submits to Hyperliquid. A coding-agent harness becomes a trading agent without being replaced.

2 · How the trading system works

All trading code lives in apps/server/src/trading/ (21 source files) plus two new workspace packages: packages/trading-contracts/ (Effect schemas) and packages/hyperliquid/ (the exchange transport + signing). Everything is Effect-TS. The design rule, stated repeatedly in the source: Hyperliquid is canonical; local tables are hints until canonical state confirms them.

The execution reactor — the closed loop

TradingMissionReactor apps/server/src/trading/TradingMissionReactor.ts:93 is the loop. It subscribes to the orchestration engine's domain-event stream, filters to four *-requested event types, and enqueues each onto a DrainableWorker (an in-process TxQueue + Effect.forever take-loop — no external broker). Each event routes to one handler:

Event Handler What it does
trading.mission-create-requested processCreateRequested Persists mission, sets status initializing, kicks the first harness run.
trading.mission-control-requested processControlRequested Pause / resume / revoke. Applies resume-exhaustion gate, reconciles, transitions state.
trading.mission-watch-fired processWatchFired Closes the wake loop — turns a fired watch into coordinator.requestRun().
trading.execution-requested processExecutionRequested The §17.2 write side: reconcile → budget → guard → submit → reconcile → re-budget.

The reactor is started by OrchestrationReactor alongside WatchEvaluator; both are forked fibers scoped to server lifetime. Every non-interrupt failure is caught (Effect.catchCause) so a refused request can never crash the queue — the mission's persisted records remain the source of truth, not the request.

Three execution-side services

HyperliquidExecutionService spends capital

apps/server/src/trading/HyperliquidExecutionService.ts:273

The only code path that spends testnet capital. Ten-step submit sequence: resolve signer → market+book → preview → map order → persist record before signing → reserve risk → sign in nonce lane → POST /exchange → inspect every per-order status → update record.

HyperliquidRe reconciler convergence

apps/server/src/trading/HyperliquidReconciler.ts:83

Pulls canonical position / open orders / fills from Hyperliquid and upserts the local migration-037 tables. Fires on 8 triggers: server-startup, ws-reconnect, before-execution, after-submission, after-fill, after-position-update, before-resume, periodic-while-open.

TradingExecutionGuard exhaustion

apps/server/src/trading/TradingExecutionGuard.ts

The §16.4 cumulative-loss gate. Pre-submit: blocks new entries when budget exhausted. Reduce-only path: closes existing positions regardless of exhaustion.

TradingBudgetReader reads

apps/server/src/trading/TradingBudgetReader.ts:59

Assembles the LossBudgetInput from the 037 tables: realised PnL + fees from trading_fills, open-position risk from snapshots, pending-entry risk from reservations. Feeds the pure evaluateLossBudget six-equation math.

The wake path — resuming the harness

When a watch fires, TradingTurnCoordinator.requestRun() apps/server/src/trading/TradingTurnCoordinator.ts:300 runs seven pre-run checks (mission active, provider binding present, instance available, lease acquirable, inbox claimable, strategy present, cause valid), acquires a decision lease via a partial unique index on trading_harness_runs, then forks a background wake fiber. That fiber calls TradingWakeupComposer.compose() to fetch a fresh market + account snapshot, serializes a bounded TradingHarnessWakeup JSON, and dispatches a normal thread.turn.start with that JSON as the resumed turn's message text.

One active run per mission — enforced by SQL. The partial unique index idx_trading_harness_runs_one_active_per_mission means a unique-violation = "queued behind active run". The coordinator retries every 5s up to 60 times, forked detached so it never stalls the reactor queue.

3 · How harnesses interact with everything

"Harness" means three different things in this repo. The dominant one is the trading harness — a durable binding between a provider/agent session and a trading mission. The other two are pure test scaffolding and a mobile screenshot script. They share nothing.

Clarify the three meanings of "harness"
Meaning Where Role
Trading harness (the product concept) TradingHarnessBinding in trading-contracts/mission.ts:21 A provider/agent runtime bound to a mission. Durable across turns; a TradingHarnessRun is one temporary turn holding the decision lease.
Test harnesses apps/server/integration/OrchestrationEngineHarness.integration.ts Assembles a real server runtime in a temp dir for integration tests. Also TestProviderAdapterHarness, VcsDriverContractHarness. No runtime role.

The trading-harness binding

A harness binding record (packages/trading-contracts/src/mission.ts:21) is: 

{
  provider,              // "claude" | "codex" | "cursor" | "grok" | "opencode"
  providerInstanceId,
  providerSessionId?,    // set when a live session exists
  resumeCursor?,         // how to resume the conversation
  threadId,              // the authority for per-call mission resolution
  model?,
  status                 // active | paused | revoked
}

Two wallets are referenced by design and never conflated: the master wallet (funded, the identity for all reads) and the execution wallet (the interim signer). Passing the execution-wallet address for account reads is a flagged programming error (execution_wallet_as_identity).

How a harness connects to the trading system

Three connections, in increasing order of side-effect:

  1. Reads — the harness calls trading_get_* tools; handlers resolve the master-wallet address from the bound mission and delegate to HyperliquidGateway. The harness never supplies an address.
  2. Writes (orchestration) — publish_momentum_strategy, register_watch, cancel_watch, request_entry dispatch orchestration commands via OrchestrationEngineService.dispatch. This puts events on the ordered WS push path so the UI updates without polling.
  3. Execution (signing) — the trading.execution-requested event is consumed by the reactor, which validates authority/budget/freshness, then signs and submits server-side. The harness is not trusted to sign.
Why the agent never signs. The agent runs in a subprocess we spawn. If we handed it the private key, any prompt-injection or tool-misuse could spend capital directly. Instead the agent expresses an intent (TradingOrderIntent); the server validates it against the mission's authority version, the loss budget, the exchange freshness windows, and the §16.3 17-item preview checklist before the signer is ever invoked. The agent's leverage is bounded to "ask".

The two bridges to trading

  1. Read bridge — read-only trading tools call HyperliquidGateway and the trading services directly inside the MCP handler effect. Synchronous, scoped to the request.
  2. Write/execution bridge — trading_request_entry does not place an order. It dispatches a command onto the orchestration engine, which becomes a persisted event, which the reactor consumes off the MCP thread to do the actual signing + submit. apps/server/src/mcp/toolkits/trading/handlers.ts:238

What is not here

  • No cloudflare-worker-mcp, no agents-mcp, no fastmcp.
  • No direct @modelcontextprotocol/sdk dependency in any package.json (transitive only).
  • No per-harness MCP server — one shared server, capability-scoped per session.
  • No .zed/ config; nothing MCP-related in .zcode/.

6 · End-to-end trade flow

From a harness tool call to a signed Hyperliquid order to a UI card. Each step is coloured by which world it lives in: pure engine, effectful trading, side-effect / exchange, settled.

2
Handler dispatches trading.execution.requested via OrchestrationEngineService.dispatch. Bearer token → scope → mission resolved from threadId. handlers.ts:245
3
Decider emits trading.execution-requested event inside a SQL transaction with the event append + projection. The decider is pure; the exhaustive default: command satisfies never makes a missing case a compile error. apps/server/src/orchestration/decider.ts:1339
4

5

Budget + guard — budgetReader.read() → evaluateLossBudget (six equations). guard.guardAction(actionType, budget) enforces §16.4 exhaustion. Reduce-only close branches separately. TradingMissionReactor.ts:349–372
7
Submit sequence — resolve signer (fail-closed) → market+book → preview (17-item checklist) → map order → persist execution record before signing → reserve risk → sign in nonce lane → POST /exchange → inspect every per-order status. HyperliquidExecutionService.ts:273 spends capital
8
Reconcile-after — reconcile(..., "after_submission") converges local state to canonical. Re-reads budget; if exhausted, transitions to blocked / cumulative_loss_limit. TradingMissionReactor.ts:398–426

Where pure stops and side-effects begin. The decider + projector are pure (deterministic, no I/O beyond the event append). Everything from HyperliquidExecutionService onward is the effectful world. The seam is TradingExecutionRequestedCommand → trading.execution-requested event (pure, persisted) → TradingMissionReactor.processExecutionRequested (effectful).

7 · Upstream T3 Code vs this fork

Upstream is T3 Code (pingdotgg/t3code) pinned at immutable tag upstream-base/2026-07-29-a8e05cbb (v0.0.31). The push remote is DISABLEd — we only pull. Every divergence is recorded in the 61 KB docs/upstream/PATCH_LEDGER.md, and every phase ends with a docs(upstream): record the PROMPT-NN upstream seams commit.

How upstream was handling it

Upstream is purely a coding-agent GUI. Its harness/provider layer (all under apps/server/src/provider/) is:

  • Drivers — one per agent (CodexDriver, ClaudeDriver, …), the process-spawning layer.
  • Adapters — protocol translation per agent, implementing ProviderAdapterShape.
  • Registries + session directory — ProviderAdapterRegistry, ProviderInstanceRegistry, ProviderSessionDirectory (thread → session/resumeCursor).
  • ProviderServiceLive — cross-provider orchestration; routes validated RPC to adapters, exposes a unified ProviderRuntimeEvent stream.
  • Orchestration — decide/project event loop, queue-based reactors (ProviderRuntimeIngestion, ProviderCommandReactor, CheckpointReactor).
  • MCP — a first-party t3-code server with a single preview capability/toolkit.

Upstream had no concept of trading, no mission aggregate, no exchange integration, and a single MCP capability. The fork's strategy was deliberately additive: preserve upstream services, extend via new product-owned packages, touch upstream-owned files only at well-documented seams.

The key architectural move

The fork made the server trading-aware by reusing the existing event-sourced loop. Trading missions are a new OrchestrationAggregateKind: "mission" flowing through the same decider/projector/reactor pipeline as chat threads. The wake path reuses upstream's ProviderSessionDirectory + resumeCursor recovery to resume a coding-agent session with a market snapshot when a watch fires. A coding-agent harness becomes a trading-agent harness without being replaced.

8 · Boundaries, invariants & gaps

The two wallets identity rule

Master wallet — funded, the identity for all reads (account/position/orders/fills). Execution wallet — the interim signer, recorded on the execution record only.

Passing the execution-wallet address for account reads raises HyperliquidIdentityError{reason:"execution_wallet_as_identity"}.

packages/hyperliquid/src/Gateway.ts:241 · errors.ts:48

The interim signer fail-closed

Loaded from env T3_TRADES_INTERIM_SIGNER_KEY or repo file .t3/secrets/hyperliquid-interim-signer-key.bin. 32-byte secp256k1. If absent or malformed, the execution service refuses — no order is signed.

apps/server/src/trading/InterimSignerConfig.ts

Nonce safety serialized

One Semaphore(1) lane per execution wallet. Monotonic ms-nonces fast-forwarded to wall clock, committed only on success. NonceRecoveryHint for restart rehydration.

packages/hyperliquid/src/NonceCoordinator.ts:56

Checkpoint decoupling separate

The git-checkpoint reactor subscribes to thread.* events only — never trading.*. It protects the harness's file edits, not exchange orders. Trading ↔ checkpoint interact only indirectly, through the bound thread.

Known gaps & honest status

End-to-end loop not yet covered by an executed integration test. ExecutionReactorLoop.test.ts:29 is it.skip — a scaffold whose fixture is in progress. Correctness currently rests on focused unit tests, the decider's command satisfies never exhaustiveness check, and a live noop signing smoke probe (executionSmoke.test.ts) that proves the signing path is byte-correct against the real exchange without spending capital.
  • netFundingUsd = 0 in the budget — no funding table yet (TradingBudgetReader caveat).
  • Open-position stop/fee fields are 0 until the PROMPT-05 protection layer writes them.
  • No modify-order action builder — only place and cancel-by-cloid.
  • Control commands restricted to pause/resume/revoke; cancel_entries/reduce_position/close_position/close_and_revoke have no command path today — close/reduce arrives as trading.execution.requested with actionType:"close"|"reduce" + reduceOnly.
  • README mismatch — the root README still reads as upstream T3 Code; the fork's identity lives in docs/, not the root README.

Verification guidance (from AGENTS.md)

  • Wait on receipts and worker drain(), never on sleeps or polling.
  • Targeted test / typecheck for the scope changed — no repo-wide checks (CI owns those).
  • Backend behavior changes ship with focused tests for that behavior.
  • A test that needs a timeout to pass is wrong.
