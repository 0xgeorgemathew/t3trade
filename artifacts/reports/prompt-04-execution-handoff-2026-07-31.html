One gate stands between this code and a live testnet order: the owner must supply an approved API-wallet key.

The full signing path is built and byte-verified against the reference SDK offline. To close the live acceptance ("Hyperliquid accepts the order"), set two env vars in the server config and a follow-up run performs the first signed testnet submission: 

T3_TRADES_INTERIM_SIGNER_KEY=0x…32-byte-hex…
T3_TRADES_INTERIM_SIGNER_ADDRESS=0x…20-byte-hex…

The wallet must be approved via the Hyperliquid testnet UI under the master account. Until both are set, the signer resolves to none and every signable action fails closed with interim_signer_not_configured. Privy replaces this in PROMPT-06.

Signing path — byte-for-byte against the reference SDK

The action-hash and EIP-712 construction was verified against @nktkas/hyperliquid src/signing/_l1.ts:

  • Domain: { name:"Exchange", version:"1", chainId:1337, verifyingContract:0x0 } — chainId is 1337, never Arbitrum's.
  • Action hash: keccak256(msgpack(action) ‖ uint64BE(nonce) ‖ vaultMarker ‖ expiresMarker); msgpack preserves insertion key order, drops undefined, widens out-of-int32 ints to bigint.
  • Phantom agent: { source: isTestnet?"b":"a", connectionId: actionHash }.

Pinning tests: the canonical Ethereum address vector (privkey = 32×0x01 → 0x7e5f…bdf) proves secp256k1+keccak are wired right; a signature-recovery round-trip proves the EIP-712 digest is correct end-to-end; action-hash determinism and insertion-order dependence are asserted.

The one test that needs the owner's key is a cross-SDK vector (sign the exact same action+nonce+key as the python SDK, compare hex). It drops in trivially once the key exists.

The signing algorithm (load-bearing)

actionHash = keccak256(
    msgpack(action)        // insertion-order keys; undefined dropped;
                           //   out-of-int32 ints widened to bigint
  ‖ uint64BE(nonce)        // 8 bytes, big-endian
  ‖ (vault ? [0x01] ‖ addr20 : [0x00])
  ‖ (expiresAfter ≠ undefined ? [0x00] ‖ uint64BE(expiresAfter) : [])
)

signature = EIP-712 sign({
  domain:     { name:"Exchange", version:"1", chainId:1337,
                verifyingContract: 0x000…000 },
  types:      { Agent: [ {source:string}, {connectionId:bytes32} ] },
  primaryType:"Agent",
  message:    { source: isTestnet ? "b" : "a", connectionId: actionHash },
})

Remaining server-side work (in dependency order)

The pure, byte-critical foundation is done. What's left is wiring it into the server's reactor/decider/projector loop — the same closed loop Phases 1–3 established.

  1. Step 3 · TradingPreviewService — the 17-item §16.3 checklist as an ordered validator (one rejection test per item) + risk reservation before signing.
  2. Step 5 · HyperliquidExecutionService — persist record → sign in the nonce lane → POST /exchange → inspect every per-order status → query canonical state → reconcile.
  3. Step 6 · HyperliquidReconciler — fills/position/open-orders via the master address; wire all eight §18.2 triggers.
  4. Step 8 · Exhaustion enforcement — reject trading_resume_mission while blocked, cancel increasing orders, preserve protection.
  5. Step 9 · Reduce-only close orchestration → reconcile to flat.
  6. Commands · Add execution commands/events to the orchestration decider (exhaustive default: never forces it) + extend the reactor.
  7. Step 10 · Thread UI — order-intent card, fill receipt, live position card from the extended mission snapshot.

Decisions (owner did not select; best judgment applied)

  • Signer: build-to-live, stop-before-submit. The capital-spending gate stays on the owner.
  • UI delivery: extend TradingMissionSnapshot + projection (single source of truth, "UI stays dumb").
  • Implementer constants: 50 bps IOC slippage, 30s reconciliation window, truncated-SHA-256 cloid — all overridable via TradingRiskPolicy.
  • Package manager: pnpm (the repo's existing lockfile + catalog + vp tooling; the prompt's own rules say pnpm). The global bun-first rule yields to an existing lockfile.
  • No runtime SDK: hand-rolled msgpack + @noble/*, matching the repo's DPoP precedent and the no-runtime-SDK decision.
