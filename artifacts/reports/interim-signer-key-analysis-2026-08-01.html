01 · The Key File

What actually lives at .t3/secrets/hyperliquid-interim-signer-key.bin?

Despite the .bin extension, the file is not binary. It is 66 bytes of ASCII hex text — a 0x-prefixed, 64-character hex string that decodes to a 32-byte secp256k1 EVM private key. This section traces exactly how it is discovered, read, and decoded into an in-memory signer.

Discovery · fs layout

The only secret in the directory

hyperliquid-interim-signer-key.bin is the sole occupant of .t3/secrets/. The directory itself is derived in apps/server/src/config.ts as <stateDir>/secrets, where stateDir resolves to .t3/dev in dev mode and .t3/userdata in production. The well-known filename constant is INTERIM_SIGNER_SECRET_NAME.

Format · read contract

UTF-8 text → hex decode

The loader (readFileText) opens the file with fs.readFile(path, "utf8") — not a binary buffer read. The text is trimmed, an optional 0x prefix is normalised, and hexToBytes splits the remaining 64 chars into 32 byte pairs. This is deliberately distinct from the generic ServerSecretStore, which treats .bin files as opaque raw bytes.

The loader pipeline

Resolution lives entirely in apps/server/src/trading/InterimSignerConfig.ts. Two sources are tried in order; both absent ⇒ fail-closed (every signable action is rejected with interim_signer_not_configured).

1. Try the environment variable first

Reads T3_TRADES_INTERIM_SIGNER_KEY and trims it. If present, this wins.

InterimSignerConfig.ts:136 · resolveInterimSignerFromEnv

2. Fall back to the secret file

Builds ${secretsDir}/hyperliquid-interim-signer-key.bin, reads as UTF-8 text. Any IO error collapses to Option.none() — the harness keeps running, just unarmed.

InterimSignerConfig.ts:150–166 · resolveInterimSignerFromFile

3. Validate against the hex-private-key regex

After normalisation, the value must match /^0x[0-9a-fA-F]{64}$/. Anything else → invalid_private_key.

InterimSignerConfig.ts:75,100 · HEX_PRIV_RE, buildSigner

4. Derive the address & cross-check

The 20-byte EVM address is derived from the key (no DB lookup). If T3_TRADES_INTERIM_SIGNER_ADDRESS is also set, it must match the derived address or the gate rejects with address_mismatch.

InterimSignerConfig.ts:110–119 · addressFromPrivateKey

5. Hand off an InterimSigner in memory

Returns { address: string, privateKeyBytes: Uint8Array(32) }. The module docstring is explicit: “held as raw bytes in memory and never persisted by this module.”

InterimSignerConfig.ts:56–61 · InterimSigner schema

The pure decider (decider.ts:1339) translates the command into a persisted trading.execution-requested event. The reactor (TradingMissionReactor.ts:330) then: reconciles canonical state before execution, assembles the preview context, enforces the §16.4 exhaustion rule, and finally calls execution.submitOrder(executionInput) at line 395.

It is also here (line 361) that the reactor resolves the interim signer address and passes it into the preview context as approvedExecutionWalletAddress — a local null-check, not an on-chain verification.

HyperliquidExecutionService.submitOrder (line 265) is the first place the key materialises. It calls signerConfig.resolve (lines 281–289). If the result is Option.none() the entire submit aborts with interim_signer_not_configured — no nonce is spent, no record written.

04 · Signing Internals

EIP-712 phantom-agent over an action hash

No ethers, no viem, no Hyperliquid SDK. The signing path is hand-rolled with @noble/curves (secp256k1) and @noble/hashes (keccak256 from sha3). The scheme is Hyperliquid’s phantom-agent EIP-712: the action is hashed, then signed as a synthetic typed-data struct — not the action itself.

Crypto deps

@noble only

@noble/curves 1.9.1 · secp256k1
@noble/hashes 1.8.0 · keccak_256

no ethers no viem no hl SDK

Chain ID

1337 (not Arbitrum)

The EIP-712 domain uses chainId: 1337 and a zero verifyingContract. This is Hyperliquid’s L1 convention — never Arbitrum 42161/421614.

Source byte

"b" for testnet

The phantom agent’s source field is isTestnet ? "b" : "a". Hardcoded isTestnet: true at the call site ⇒ source is always "b" here.

The digest, end to end

packages/hyperliquid/src/Signing.ts — phantom-agent digest 
// 1. ACTION HASH — the "connectionId" of the phantom agent
//    keccak256( msgpack(action) ‖ uint64BE(nonce) ‖ vaultMarker ‖ expiresMarker )
const actionHash = createL1ActionHash({
  action, nonce,
  // vaultAddress: undefined, expiresAfter: undefined (unused here)
});

// 2. EIP-712 DOMAIN (chainId 1337, zero verifyingContract)
const DOMAIN = { name: "Exchange", version: "1", chainId: 1337, verifyingContract: "0x000…000" };

// 3. PHANTOM AGENT STRUCT  Agent(string source, bytes32 connectionId)
const structHash = keccak256(
  AGENT_TYPE_HASH          // keccak256("Agent(string source,bytes32 connectionId)")
  ‖ keccak256(source)           // source = "b"   (testnet)
  ‖ actionHash              // the connectionId (32 bytes)
);

// 4. FINAL DIGEST  =  keccak256( 0x1901 ‖ DOMAIN_SEPARATOR ‖ structHash )
const digest = keccak256(0x1901 ‖ DOMAIN_SEPARATOR ‖ structHash);

// 5. SIGN with the 32 bytes from the .bin file
const raw = secp256k1.sign(digest, privateKey);   // { r: Uint8Array(32), s: Uint8Array(32), v: 0|1 }

// 6. BIAS v to Ethereum convention and hex-encode for the wire
return {
  r: "0x" + bytesToHex(raw.r),
  s: "0x" + bytesToHex(raw.s),
  v: raw.v === 0 ? 27 : 28,            // Ethereum recovery id
};

Critical invariants (load-bearing)

Object key insertion order is part of the hash. The custom msgpack encoder preserves the order keys were added to the object literal — reordering fields changes the hash and invalidates the signature. The Hyperliquid backend rejects any signature computed over a reordered struct.

Msgpack.ts:36–54 — ordered encode
// insertion order is significant — do not sort keys
for (const [key, value] of Object.entries(obj)) { // ← order from the literal
  encodeStr(key);
  encode(value);
}

Optional fields are dropped, not null-encoded. An undefined entry is skipped entirely. This is why the action struct intentionally omits fields rather than setting them to null — a stray null would change the msgpack output and break the signature.

Integers that overflow int32 are widened to bigint. Nonces are millisecond timestamps (~13 digits) — far above int32. The encoder detects this and emits them as msgpack bigint (uint64) rather than truncating. Getting this wrong silently breaks every signature after the year 1970+~24d.

Signing is serialized by a single-permit semaphore. The NonceCoordinator guarantees strictly-monotonic nonces even under concurrent execution requests: the “assign nonce → sign → submit” critical section runs one at a time per wallet. The nonce itself is Clock.currentTimeMillis (Effect’s testable clock), fast-forwarded past the last issued value if wall clock has drifted backwards.

06 · Safety & Scope

What this key does — and does not — do today

Strictly the current scope of feature/trading-04-execution. Future work (PROMPT-06 Privy integration, mainnet, agent-approval) is explicitly out of scope and called out only to mark the boundary.

In scope now

What the key authorises

  • Signing testnet L1 order actions (open, scale-in, reduce, close).
  • The noop action in the gated smoke test.
  • Recording its own derived address as signer_address on each execution record.
  • Being the “approved execution wallet” for the local preview null-check (POC collapse).

Out of scope / deferred

What the key does NOT do

  • No mainnet — only api.hyperliquid-testnet.xyz is configured.
  • No approveAgent — the on-chain agent-approval action is not implemented.
  • No cancel on the wire — the buildCancelByCloidAction builder exists but has zero call sites.
  • No Privy — the interim key is a manual stand-in until PROMPT-06.

Fail-closed guarantees

Key absent

Both env var and file missing ⇒ Option.none() ⇒ every signable action rejected with interim_signer_not_configured. No nonce spent.

Malformed key

Fails the /^0x[0-9a-fA-F]{64}$/ regex ⇒ invalid_private_key. The harness stays up, just unarmed.

Address mismatch

If T3_TRADES_INTERIM_SIGNER_ADDRESS is set and disagrees with the derived address ⇒ address_mismatch rejection.

Operational hygiene

How the key is protected at rest

  • File mode 600 — owner read/write only.
  • Directory mode 700 on .t3/secrets/.
  • Held as Uint8Array(32) in memory; never logged, never persisted by the signer module.
  • Never written into trading_accounts.master_wallet_json or execution_wallet_json (both schemas are key-less by design).
  • Loaded via the dedicated InterimSignerConfig reader, deliberately bypassing the generic ServerSecretStore raw-byte path.
