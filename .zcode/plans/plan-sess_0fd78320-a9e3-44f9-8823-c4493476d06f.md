## M1 — Execution command, event, and reactor handler (keystone)

**Contracts** (`packages/contracts/src/trading.ts` + `orchestration.ts`), mirroring the mission-control pattern exactly:

- New internal command `TradingExecutionRequestedCommand` (`type: "trading.execution.requested"`, fields: `commandId, threadId, missionId, intent: TradingOrderIntent, expectedAuthorityVersion, activeHarnessRunId, createdAt`). Add to `InternalTradingCommand` (server-raised, like `status-set`/`strategy-published`, not client-dispatchable — the harness does not place orders directly).
- New event `trading.execution-requested` with a `TradingExecutionRequestedPayload` (`{ missionId, threadId, intent, expectedAuthorityVersion, activeHarnessRunId, requestedAt }`). Add to `TRADING_EVENT_TYPES`, `OrchestrationEventType`, and the `OrchestrationEvent` struct union. The `intent` is re-used from `packages/trading-contracts/src/execution.ts` (`TradingOrderIntent` already encodes `strategyVersion`, `executionSequence`, `actionType`, `stop`, `reduceOnly`).

**Decider** (`apps/server/src/orchestration/decider.ts`, before `default: never` at L1266):

- `case "trading.execution.requested"`: `yield* requireThread(...)`, then `return { ...(yield* withEventBase({ aggregateKind:"mission", aggregateId: command.missionId, occurredAt: command.createdAt, commandId: command.commandId })), type:"trading.execution-requested", payload:{...} }`. Mirrors the control case. The exhaustive `never` then type-checks.

**Reactor** (`apps/server/src/trading/TradingMissionReactor.ts`): subscribe to `trading.execution-requested` in addition to the two `*-requested` events. New `processExecutionRequested` handler that runs the §17.2 write side:

1. Load mission via `missions.getMission(missionId)` → `tradingAccountId`, `market`.
2. Resolve `masterAddress = missions.getMasterWalletAddress(mission.tradingAccountId)`.
3. Build `PreviewContext` from mission + authority + budget (loaded from the 037 reservation/position tables — a small `TradingLossBudgetSnapshot` reader, see M2) + `activeHarnessRunId` from the event payload.
4. `guardAction(intent.actionType, budget)` (M4).
5. `execution.submitOrder({ intent, previewContext, allowedSlippageBps: 50 })` — this persists+reserves, signs in the nonce lane, POSTs, inspects.
6. `reconciler.reconcile({ missionId, masterAddress, market }, "after_submission")` (M2).
7. If the post-submit budget is exhausted → `blockForExhaustion(missionId, expectedVersion)` (M4).
8. Re-validate preview items 4 & 8 (see Hardening) or document the deferral.

- The existing `catchCause` log-warning absorbs a refused/failed execution without crashing the reactor.

## M4 — Runtime exhaustion enforcement (parallel with M2/M5)

- **Auto-block**: in the M1 reactor handler, after `submitOrder` + `after_submission` reconcile, re-evaluate the loss budget; if `remainingCumulativeLossUsd ≤ 0`, call `blockForExhaustion(missionId, expectedVersion)` (transitions to `blocked` / `cumulative_loss_limit`). Re-check **inside** the nonce lane is already covered by the preview's `reservationsPlusProposedWithinBudget` check (`TradingPreviewService.ts:209`), which runs after reservation persists, before sign — so the choke point is already the serialized lane.
- **Gate resume**: in `TradingMissionReactor.processControlRequested`, before `missions.transition`, load the mission (`getMission`), compute `isBlocked = mission.status === "blocked" && mission.blockedReason === "cumulative_loss_limit"`, and call `guardResume(missionId, isBlocked)`. A refused resume `Effect.fail`s and is caught by the existing `catchCause` → logged, projection keeps `blocked`. No auto-resume (explicit user action only, per §16.4).
- Note: `getMission` + `getMissionVersion` are two reads (the mission contract has no `version` field) — acceptable, matches existing reactor pattern.
