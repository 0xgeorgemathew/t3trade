## Step 2 — WatchEvaluator (candle-close once, price-cross fresh, scheduled reassessment)

`apps/server/src/trading/WatchEvaluator.ts` (new). Subscribes to `HyperliquidWebSocketClient` (PROMPT-02) for the markets/intervals that have active watches; evaluates on each delivery:

- `candle_close` — fire only when the candle's close time has passed (final close); track seen `(watchId, closeTime)` so the **same closed candle fires exactly once**; mark watch `active → triggered`, persist inbox event with key `candle_close:<interval>:<closeTime>`.
- `price_cross` — evaluate against fresh BBO/mark (`bboFreshness` 2s, `assetFreshness` 5s from `Gateway.ts:110-115`); on cross, mark triggered + inbox key `price_cross:<market>:<direction>:<price>`.
- `scheduled_reassessment` — a periodic sweep modeled on `ProviderSessionReaper` (`Effect.forkScoped` + `Schedule.spaced`, short interval ~1s) that fires watches whose `runAt <= now`.
- `order_update` / `position_update` — fire from account-stream deliveries (clearinghouse/orders) for the watched cloid/market.
  On any fire: `TradingEventInbox.persist` + `TradingWatchService.markTriggered` + dispatch `trading.mission.watch-fired` (UI refresh). Shape: `WatchEvaluatorLive` layer + `{ start, drain }` like `TradingMissionReactor`.

Test (minimal, required by acceptance): `WatchEvaluator.test.ts` — with a fake WS client, **replaying the same closed candle twice fires exactly once** (assert one inbox row, watch `triggered`).

**Gates.** Commit `feat(trading): PROMPT-03 step 2 — watch evaluator`.

## Step 4 — TradingTurnCoordinator (7 pre-run checks, single lease)

`apps/server/src/trading/TradingTurnCoordinator.ts` (new). `requestRun(input: HarnessRunRequest): Effect<HarnessRunOutcome>`. Runs the §12.3 checks **in listed order**: (1) mission active, (2) provider binding unchanged, (3) provider instance available, (4) no other run owns the lease, (5) account available, (6) event not superseded, (7) latest strategy/authority versions loaded. Lease acquisition = `INSERT INTO trading_harness_runs (status='starting')`; the partial unique index `idx_trading_harness_runs_one_active_per_mission` (`035:136`) makes a concurrent second insert a unique violation → caught and returned as `queued_behind_active_run` (never a second live run). Returns `blocked{reason}` for any failed check. Exposes `markRunCompleted(runId)` / `markRunFailed(runId)` for the wake-path completion callback.

Test (minimal, required by acceptance): concurrency — two simultaneous `requestRun` for the same mission yield exactly one `started` and one `queued_behind_active_run`; assert only one non-terminal row in `trading_harness_runs`.

**Gates.** Commit `feat(trading): PROMPT-03 step 4 — turn coordinator and decision lease`.

## Step 5 — Wake path (assemble TradingHarnessWakeup, dispatch thread.turn.start)

`apps/server/src/trading/TradingWakeupComposer.ts` (new, pure-ish): assembles `TradingHarnessWakeup` from fresh `HyperliquidGateway.getMarketSnapshot`/`getAccountSnapshot`, `TradingStrategyService.getCurrentStrategy`, the mission's `authority`, `TradingEventInbox.collectPending`, and the mission `instruction`.
`TradingTurnCoordinator` — after a `started` outcome, mark the pending events `included_in_run`, build the wakeup, serialize it into `ThreadTurnStartCommand.message.text` as a structured payload (`{ kind: "trading-harness-wakeup", wakeup }`), and `engine.dispatch({ type: "thread.turn.start", commandId, threadId, message: { messageId, role:"user", text, attachments: [] }, createdAt })`. **Dispatch only — never call `ProviderService` directly** (ProviderBoundary). `ProviderCommandReactor` + `ProviderService` own ensure-session and `sendTurn`; same-instance resume applies the persisted `resumeCursor` automatically.

Test (minimal, required by acceptance — the keystone): end-to-end through the orchestration integration harness — after a watch fires, `engine.dispatch(thread.turn.start)` reaches the provider and the resumed session has the **same `providerSessionId`** as the original; fresh snapshots are carried in the wakeup.

## Acceptance mapping

- Final candle fires exactly once → Step 2 test.
- T3 stays active after the turn → Step 5 (reactor-driven wake, server never goes idle on `turn.completed`).
- Same provider session resumes via `ProviderService` → Step 5 keystone test (`providerSessionId` unchanged).
- Single lease prevents duplicate/concurrent runs → Step 4 test.

## Risks / blockers

- The end-to-end resume test (Step 5) needs the orchestration integration harness; if dispatch does not resume the session at baseline, STOP and report the failing call verbatim (prompt's blocker rule).
- `HarnessRunRequest` is "pinned in the wake-up phase" per §12.3 — defined here in Step 0.
- Wake latency must stay ≪ `QUEUED_TURN_START_GRACE_MS` (2 min); the periodic sweep interval is tuned accordingly.
